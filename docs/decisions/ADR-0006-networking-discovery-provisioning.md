# ADR-0006: Networking, Discovery, and Provisioning

## Status

Accepted

## Context

[networking.md](../architecture/networking.md) describes Core's networking
responsibilities under CLAUDE.md's local-first philosophy. Three decisions
within that scope involved real tradeoffs and rejected alternatives: how a
module's external-service calls retry after a failure, whether Core
provides a shared LAN discovery mechanism, and how the device gets onto
Wi-Fi in the first place. This ADR records those, so the architecture doc
can state the current design without carrying the full rationale inline.

## Decision: Retry/backoff policy ownership

**Options:**
- A shared Core utility (a generic exponential-backoff helper) every module
  uses for its external-service calls.
- Each module implements its own retry policy suited to its external
  service's specific characteristics.

**Decided:** a shared Core backoff utility as the default, with modules
allowed to layer service-specific reconnection semantics on top where the
external protocol requires it (e.g. WebSocket reconnect/resubscribe logic
for Home Assistant). This avoids every module reimplementing basic backoff
without forcing a one-size-fits-all reconnection model onto integrations
with genuinely different transport characteristics (Home Assistant's
WebSocket reconnect semantics differ meaningfully from an HTTP-polling
integration like Uptime Kuma). Worth re-checking once the second module
(Kodi) is built, since a single module isn't enough to validate the shared
utility actually fits multiple integrations' needs — but the default is
settled.

## Decision: LAN discovery service shape

**Options:**
- A full generic Core discovery abstraction covering every module's
  discovery protocol behind one interface.
- No Core discovery service at all — every module implements its own.
- A thin Core wrapper around standard mDNS/Zeroconf only, for the modules
  that actually use it.

**Decided:** the third option. Core wraps ESP-IDF's `mdns` component for
modules whose external service supports standard mDNS/Zeroconf discovery —
Home Assistant and Kodi both do. This is deliberately not a universal
discovery abstraction: Harmony Hub discovery uses a proprietary UDP
broadcast protocol that doesn't fit an mDNS shape, and Uptime Kuma has no
discovery protocol at all (manual URL entry). A full generic abstraction
was rejected because forcing those into one generic Core interface would
repeat the exact mistake [ADR-0003](ADR-0003-module-architecture.md) warns
against — designing a Core abstraction before real module needs have
validated its shape (notably, it wouldn't even cover Harmony, the first
module that needs discovery). No Core service at all was rejected because
it means genuine duplicated mDNS-browsing code between at least two modules
that would otherwise want identical logic. Harmony's discovery logic stays
entirely inside the Harmony module either way.

## Decision: Initial Wi-Fi provisioning flow

**Context:** the device has no Wi-Fi credentials out of the box, so it
can't serve its own setup UI over the LAN the way the rest of the Web
Management UI does. The device has its own touchscreen, which is unusual
for this class of problem (most ESP32 IoT devices are headless), but a
long random Wi-Fi password is much easier to paste from a password manager
into a browser than to type on a touchscreen keyboard.

**Options:**
- Touch UI first, on-screen keyboard entry as the primary path.
- SoftAP + captive portal (browser-based, via ESP-IDF's `wifi_provisioning`
  component) as the primary path, Touch UI keyboard as fallback.
- Touch UI + camera-based QR-code scan (using the Tab5's onboard camera to
  scan a Wi-Fi QR code generated by a phone) as the primary path.
- Both SoftAP and camera QR scan, as equal alternate paths.

**Decided:** SoftAP + captive portal as the primary path, via ESP-IDF's
`wifi_provisioning` component, with Touch UI on-screen keyboard entry
remaining available as a fallback for users without a second device handy.

Touch-UI-only was rejected because it doesn't solve the complex-password
problem at all. The camera QR-code option was rejected — and is worth
recording why, since the Tab5's onboard camera made it a genuinely
plausible option: it would mean bringing up an entirely separate,
currently-unverified hardware subsystem (MIPI-CSI camera driver, QR decode
library — see [hardware.md](../architecture/hardware.md#camera-out-of-current-scope))
for a screen that runs once per device in the common case. `wifi_provisioning`
is a well-trodden ESP-IDF component that reuses HTTP server infrastructure
already committed to in [ADR-0002](ADR-0002-technology-stack.md), with no
new hardware bring-up risk — not worth taking on the camera risk for
redundant coverage of the same problem. "Both" was rejected for the same
reason: it pays the camera risk on top of the SoftAP work for no clear
additional benefit.

One consequence of this choice: the SoftAP captive portal is scoped
narrowly to collecting Wi-Fi credentials only, not the Web UI's admin
password — see [ADR-0007](ADR-0007-web-management-ui-policies.md#decision-when-the-admin-password-is-set)
for that sequencing decision.

## Consequences

- [networking.md](../architecture/networking.md) states the resulting
  design (Core's networking responsibilities, the provisioning flow, the
  discovery wrapper) without repeating the rejected alternatives.
- The camera-QR rejection is also recorded in
  [hardware.md](../architecture/hardware.md#camera-out-of-current-scope) so
  it isn't silently re-proposed later without this context.
- If a second module's discovery needs don't fit the mDNS-only shape, that
  is a signal to revisit this ADR, not to quietly special-case it in Core.
